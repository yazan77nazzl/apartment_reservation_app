# Reconstruction decisions

1. The report is the primary reference. This is reconstructed code, not recovered original code. Chapters 1–7 and all diagram/screenshots were inspected. The attached master request adds security, localization, notifications and testing detail beyond the report.
2. Student and owner are the only roles. Role cannot be changed after registration. Self-registration is not university identity verification; university database integration is explicitly future work in Chapter 7.
3. A reservation leases a whole room, including its beds. The report does not specify independent bed inventory. Intervals are half-open [start, end) in UTC calendar dates; back-to-back reservations are allowed.
4. Currency is ILS. Prices are monthly integer minor units; a period costs ceil(days / 30) months. This explicit policy replaces unspecified report pricing. Quotes are captured at request time and shown before submission.
5. Owner approval enters `awaiting_payment` directly, representing approved but unpaid. Such reservations hold inventory until cancelled/expired; holds expire after 24 hours. Payment success becomes `confirmed`; failed sandbox attempts remain payable. Past confirmed stays display completed and are eligible for history/renewal. No paid reservation can be cancelled without a production refund policy.
6. Availability is a manual listing switch plus dated confirmed/unexpired approved reservations. Pending requests do not block inventory. Approval and payment serialize on the same room document, so concurrent requests cannot claim overlapping periods.
7. Renewals create linked, separate requests beginning at the previous end (or today if expired), preserving payment and approval history.
8. Reviews require a confirmed paid stay that has begun, one review per student/apartment. Users can update their own review via backend; owners cannot alter ratings.
9. The original card screenshot is replaced by an explicitly labelled sandbox success/decline checkout, with no card entry. Demo checkout is callable only under emulator execution. Real payments require provider creation/webhook verification and refunds; no production provider is configured.
10. The report abstract mentions videos but documents only image upload screens. Video publishing, bank integration, parent monitoring, subscriptions and university integrations are excluded as unimplemented scope/future work.
11. Profile email/password updates use Firebase reauthentication. Verified new-email changes synchronize the private Firestore profile on next session refresh; passwords never enter Firestore.
12. Push notifications are supplemental. In-app Firestore notification records always exist; FCM requires actual platform configuration and permission. Android/iOS platform runners must be generated with Flutter when the SDK is available; no APK is claimed.
13. The user subsequently required Spark billing and no Storage. Default live mode now uses direct rules-protected Firestore operations, conservative single-room approval locks, bundled demo images and no real checkout. The full trusted dated-booking/payment flow runs in local emulators. Native runners were generated after installing a local SDK. Full production payment confirmation cannot safely be moved into client code.
